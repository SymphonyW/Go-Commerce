# Go Commerce 项目面试文档

这份文档不再只写“微服务常见八股”，而是围绕当前项目真实实现来回答。面试时最有说服力的，不是概念背得多熟，而是能把问题落回代码路径、事务边界和取舍。

## 1. 为什么金额不能由前端传入？

因为前端输入不可信。
当前项目创建订单时，客户端只提交 `product_id` 和 `quantity`；订单服务会在数据库里读取真实商品价格，重新计算 `total_amount`，并把商品名称、价格写成订单快照。

这样能解决两类问题：

1. 用户篡改金额
2. 商品后续改价后，历史订单展示被污染

对应实现：`internal/order/service.go`

## 2. 如何防止库存超卖？

项目没有采用“先查库存，再减库存”的两步方案，而是直接做条件更新：

```sql
UPDATE products
SET stock = stock - ?
WHERE id = ? AND stock >= ?;
```

如果 `RowsAffected = 0`，再判断是商品不存在还是库存不足。
这让并发扣减在数据库层一次完成，避免两个请求都读到“库存还够”后一起扣成负数。

对应实现：`internal/product/stock.go`

## 3. 如何实现订单超时取消？

当前项目使用 RabbitMQ 原生 `TTL + DLX`：

1. 创建订单后投递 `order.timeout.check`
2. 消息先进入延迟队列
3. TTL 到期后进入死信交换机
4. 订单服务消费超时消息
5. 如果订单仍是 `pending`，走统一取消流程
6. 写入 `cancel_reason = payment_timeout`，回补库存，并产生取消事件

这个方案的优点是部署简单，不依赖额外 delayed-message 插件。
人工取消和超时取消复用同一套事务逻辑，因此重复消息不会导致库存二次回补。

对应实现：

- `internal/order/timeout.go`
- `internal/order/timeout_consumer.go`
- `internal/order/service.go`

## 4. 为什么引入 RabbitMQ？

因为项目里有两类动作不适合强行塞进同步请求：

1. **支付成功后推动订单状态变更**
2. **下单成功后的异步通知**

RabbitMQ 让这些消费者和主交易链路解耦：

- 支付服务只负责确认“支付成功”
- 订单服务异步消费 `payment.succeeded`
- 通知服务异步消费 `order.created`

这样后续如果要加积分、营销、履约等消费者，不需要继续把调用链拉长。

## 5. 什么是 Outbox Pattern？为什么这个项目需要它？

数据库事务和 MQ 发布不是同一个原子资源。
如果先写数据库、再发 MQ，后半段失败时就会出现“业务成功，但事件丢失”。

当前项目的做法是：

1. 在业务事务里同时写业务表和 `outbox_events`
2. 提交成功后，由 `outbox-worker` 异步投递 RabbitMQ
3. 失败时按退避策略重试

它把“消息是否可靠送达”的问题，从一次脆弱的网络调用，变成了一个可观测、可补偿、可重试的后台任务。

对应实现：`internal/outbox/`

## 6. 如何保证幂等性？

这个项目要分层说，不能一句“用了幂等键”带过。

### 已真正落库的幂等

`POST /api/orders`

- `Idempotency-Key` 必填
- 以 `user_id + request_path + key` 唯一约束
- 同 key 同请求会回放首次响应
- 同 key 不同请求会报冲突

### 语义上幂等，但还没做到完整重放

- 取消订单
- 支付成功

这两个接口当前依靠状态机做到“重复调用不产生重复副作用”，但还没有像下单那样把首次响应稳定回放出来。
如果面试官继续追问，这是一个很好的延展点：**下一步应把下单的幂等表机制推广到这两个写接口。**

## 7. 商家权限如何设计？

项目采用两层校验：

1. **网关层**：校验 JWT，确认角色是否为 `merchant` 或 `admin`
2. **服务层**：重新查询数据库里的真实角色与 `owner_user_id`

普通商家只能操作自己名下店铺，`admin` 才能跨店操作。
这样做是因为 `merchant_id` 来自客户端，不能当作授权依据。

对应实现：`internal/merchant/service.go`

## 8. 订单状态机如何保证合法流转？

当前主链路是：

```text
pending -> paid -> shipped -> completed
pending -> cancelled
```

所有状态变化都统一通过：

- `ValidateTransition`
- `TransitionTo`

因此不会出现：

- `cancelled -> paid`
- `paid -> completed`
- `completed -> cancelled`

支付成功消费、发货、确认收货、取消订单，都会复用这套状态机规则。

对应实现：`internal/order/status.go`

## 9. 如何做链路追踪？

当前项目已经实现的是**链路关联**，还不是完整分布式追踪：

- API Gateway 生成或透传 `X-Request-ID`
- 同时维护 `X-Trace-ID`
- gRPC metadata 继续传递这些字段
- 领域事件也会携带 `request_id` 和 `trace_id`

这样即便事件由 Outbox 延迟发布，也还能回溯到原始请求。
如果要升级到真正的分布式追踪，下一步应接入 OpenTelemetry，并把 span 打到所有服务。

对应实现：

- `pkg/observability/context.go`
- `pkg/observability/grpc.go`
- `pkg/events/order.go`

## 10. 为什么支付成功不是同步直接改订单？

因为“支付”和“订单”是两个业务边界：

- 支付服务负责支付尝试与结果
- 订单服务负责订单状态

当前项目通过 `payment.succeeded` 事件让订单服务自己把 `pending` 改成 `paid`。
这样比“支付服务直接改订单表”更清晰，也更利于未来接入账务、风控、通知等下游。

## 11. 为什么订单项要保存 `merchant_id` 快照？

因为商品归属可能变化，但历史订单不能跟着漂移。
下单时把 `merchant_id` 写进 `order_items`，可以保证：

- 历史归属稳定
- 商家查看订单时不依赖后续商品归属反查
- 混合商家订单能按订单项裁剪

这是一个“多写一点，换历史语义稳定”的建模选择。

## 12. 项目当前仍有哪些不足？

这是很适合主动说清楚的一题。

| 不足 | 为什么重要 |
| --- | --- |
| 多服务共享同一 MySQL 数据库 | 进程拆分已有，数据边界还没真正独立 |
| 观测能力主要落在网关 | 还没形成全链路统一指标与追踪 |
| 取消 / 支付成功缺少完整幂等回放 | 目前是语义幂等，不是稳定响应重放 |
| 网关错误映射不完全统一 | 某些历史接口仍会把下游错误打成 `500` |
| 前端尚未自动附带 `Idempotency-Key` | 后端能力还没完全融入用户体验 |
| 支付还是 mock | 能演示流程，不能代表真实支付系统 |
| 公开商家列表、用户订单列表未暴露分页 | 服务层支持，网关层还没接完整 |

如果要把项目继续拔高，最值得先做的不是“再加一个新功能”，而是把这些已经暴露的工程边界补齐。

## 13. 一句话总结这个项目

它不是一个“把 CRUD 堆在一起”的练手项目，而是一个已经把**交易一致性、异步事件、超时补偿、权限边界和工程验证**串起来的电商微服务样板。
